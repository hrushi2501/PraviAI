## Priorities and credential boundaries

1. **Before claiming secure hosted operation:** verify dedicated restricted application and identity-worker credentials. `DatabaseSession.system()` currently shares the single base `db` pool; normal runtime `SET LOCAL ROLE` alone does not prove base login least privilege. Fix the explicit credential separation and privileged identity path using existing clients/env, then run actual role-level negative tests.
2. **Complete necessary external workflows:** actual Clerk invitation dispatcher and parent-authorized evidence upload/private delivery with reliable retry/reconciliation. Provider configuration and signed delivery tests are required; no fake success defaults.
3. **Low-dependency repository safeguards:** existing Bun CI, consistent validation/error envelopes, redacted correlation logging, tested headers, bounded liveness/readiness and distributed rate limiting. Implement after concrete UI remains functional and known config boundaries are documented.
4. **Acceptance evidence:** real disposable action/repository integration and independent-user E2E; provider retry settings and restore drill; measured pool/query plans. Credentials and allowed live/disposable target must be confirmed without printing secrets.
5. **Defer unless justified:** Storybook, general flags, broad email notification suite, OpenAPI for action-only UI, mandatory Clerk org synchronization, blanket partitioning, replacement logging/ORM/queue frameworks.

Repository file absence cannot determine whether Vercel/Supabase/Clerk account controls exist. Never claim unavailable provider backup, retry or security-header settings are verified absent. No network/provider verification was performed for this checklist; review those account configurations through authorized credentials in a separate infrastructure phase.


## Deep-report corrections and canonical SQL inventory

The canonical schema is `schema.sql`, with Drizzle declarations acting as application mappings; Drizzle table metadata alone is not an inventory of installed PostgreSQL controls. A text scan of the current schema counts 36 `CREATE TABLE` declarations, 140 CHECK expressions, 42 explicit index statements, 23 trigger-declaration strings, 37 composite foreign-key clauses plus 109 inline references, 24 policy-declaration strings and 100 functions. These are source occurrence counts, **not installed catalog counts**: dynamic loops add per-table RLS and revision/audit triggers. The existing real-SQL harness checks all installed application tables for enabled RLS and exercises invalid mutations, denied direct writes, independence and immutable history; 38 groups passed at the recorded schema hash. Thus claims of zero checks/RLS/update triggers/FK indexes are incorrect. `SCHEMA_ARCHITECTURE.md` and installer/migration boundaries must remain authoritative over an incomplete introspection of `src/db/schema/*.ts`.

Do not “repair” this by blindly adding 35 enums or 96 indexes. Versioned configurable lifecycle states deliberately cannot be replaced by a universal enum. Some ORM declarations omit SQL-owned CHECKs/triggers/policies, so a broad Drizzle schema push is unsafe; use reviewed migrations preserving canonical controls. Measure actual FK/query paths before adding an index.

Other new-report claims are also inaccurate: workspace/dashboard operations are wrapped in `withAuthenticatedAction` and actor-scoped `withQuery`; SQL RLS/capability checks apply to the actual reads. Directory membership existence checks are correlated SQL within bounded set-based queries, not an application per-user N+1 loop. The page may perform multiple independent bounded queries, which can be measured without inventing one network call per user. `src/app/app/error.tsx` exists, so “no error boundary” is false. Legacy preview modules remain in source, but their presence does not demonstrate fixture/persona use by current database-backed production routes. Inspect route imports and runtime wiring before describing a live coupling.
